# web-research Skill

## 决策顺序

1. **先判断要不要联网**：问题指向"当前项目 / 当前文件 / 当前代码"时，用 `glob_files` / `grep_code` / `read_file`，不要联网。只有外部事实、时效信息、第三方产品才联网。
2. **没有 URL** → `web_search` 找入口，看标题与摘要选出 1~2 个候选。
3. **已有 URL** → 先 `web_fetch` 读正文；只有 fetch 失败或正文为空时才回到 `web_search`。
4. **够了就停**：一个能回答用户问题的页面 > 抓十个不相关页面。

本环境没有浏览器自动化（无 CDP / 无 Chrome DevTools MCP）。不要假设能执行点击、填表、读登录后页面；遇到这类需求直接说明能力边界，并给出可替代的公开信息路径。

## 工具选择表

| 场景 | 首选 | 说明 |
|---|---|---|
| 关键词搜索、找入口 | `web_search` | 拿到标题 / URL / 摘要后先判断相关性 |
| URL 已知，要正文 | `web_fetch` | 正文会转 Markdown，适合博客、官方文档、README |
| web_fetch 返回空正文 / 只有导航 | 换 URL 形态后重试一次，再退回 `web_search` | 见 `references/site-patterns.md` |
| 需要多源事实核对 | `web_search` + 多个 `web_fetch` | 至少两个独立来源 |
| 抓取需要登录 / 验证码 | 放弃抓取 | 明确告知用户需要手动提供内容 |

## 抓取失败的处理

按成本从低到高，每级只试一次，不要在同一条路径上反复重试：

1. 换 URL 形态：加 `?plain=1` / 去掉追踪参数 / 用 `raw.githubusercontent.com` 读 GitHub 文件。
2. 退回搜索摘要：用 `web_search` 的结果拼出事实，并注明"来自搜索摘要，未读到原文"。
3. 明确失败：告诉用户哪个 URL 抓不到、可能的原因（防爬 / 登录 / 动态渲染），需要用户提供正文。

## 内容校验

- **时效**：优先看页面上的发布日期 / 版本号；与用户问题的时间范围不符时主动说明。
- **版本**：API 与配置项以官方文档当前版本为准，不要用记忆里的旧版本号。
- **截断**：`web_fetch` 有字符预算，明确看到 `...` 截断时不要假装读过后面内容。

## 输出规范

- 引用来源时给出 URL，并区分「原文事实」与「我的推断」。
- 多来源冲突时并列写出差异，不要静默选一个。
- 调研类问题先给结论，再给证据；不要把抓取过程写成流水账。

更细的站点点位与 URL 形态见 `references/site-patterns.md`，需要时用 `read_skill_file` 读取。
